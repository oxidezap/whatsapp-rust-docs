## Choose the creation type

Use `polls().create` for single or multiple selections. Use `create_quiz` with a correct option index for a quiz. Both return `CreatedPoll` and carry the secret and creator needed by later votes.

```rust
use whatsapp_rust::{Client, Jid};

async fn quiz(client: &Client, chat: &Jid) -> whatsapp_rust::anyhow::Result<()> {
    let options = vec!["A".to_owned(), "B".to_owned()];
    let created = client.polls().create_quiz(chat, "Choose A", &options, 0).await?;
    let target = created.poll_ref()?;
    client.polls().vote(&target, &["A".to_owned()]).await?;
    Ok(())
}
```

## Keep the parent association

Save the creation message ID, destination, actual crypto creator and secret together. To rebuild a reference for an incoming poll, use its `InboundMessage::message_ref()`, the original creator and a validated `MessageSecret`. A message reference by itself does not include the crypto secret.

When processing updates, `decrypt_vote(ciphertext, &target, voter).await` returns selected option hashes. Map hashes to the creation's option names or use `aggregate_votes` for a tally. Preserve voter identity and update order when building a custom aggregate.

## Handle unavailable secrets

A received update cannot be decrypted without its parent secret. Implement the named validated [storage read](/api/store#msgsecretstore) and retain the parent timestamp when known. History-sync and inbound processing can seed that store, but an application must not assume every parent is available.
