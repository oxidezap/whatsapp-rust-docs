## Backend

Implement `SignalStore`, `AppSyncStore`, `ProtocolStore`, `MsgSecretStore` and `DeviceStore`; the blanket implementation supplies `Backend`. Use the source trait reference for exact signatures and required/default method distinctions.

| Domain | Preserve |
| --- | --- |
| Signal | Session/sender-key writes and durable pre-wire ordering |
| App state | Key, version and mutation-MAC consistency |
| Protocol | Identity mappings, pending payloads and crash replay boundaries |
| Message secrets | Validated reads, parent timestamps and deterministic retention merges |
| Device | One account's persistence and lifecycle scope |

Use [storage concepts](/concepts/storage) for the ownership model and [custom backends](/guides/custom-backends) before implementing an adapter. A collection of copied SQL snippets is not a complete backend contract.

## MsgSecretStore

The named read validates key material and preserves the parent's timestamp. The required methods are `put_msg_secrets`, `get_stored_msg_secret` and `delete_expired_msg_secrets`. `put_msg_secret` is a single-entry default write; `get_msg_secret` is a byte-only default projection of the named read. There is no `get_msg_secret_with_ts` fallback.

```rust
use whatsapp_rust::StoredMessageSecret;
use whatsapp_rust::wacore::store::error::Result;

fn decode_row(bytes: &[u8], stored_parent_time: i64) -> Result<StoredMessageSecret> {
    StoredMessageSecret::from_stored_bytes(bytes, stored_parent_time)
}
```

The result contains a validated `MessageSecret` and `message_ts: Option<i64>`. A persisted zero maps to `None`; retain a known parent time. For a backend that never stored timestamps, explicitly return `StoredMessageSecret::new(secret, None)`. Do not substitute a row creation time or expiry deadline for the parent's event time.

Malformed persisted bytes return `StoreError::InvalidMessageSecret`. Reads must not pad, truncate or log the bytes. The `MessageSecret` wrapper redacts its debug output; explicitly exporting its bytes still exposes the secret.

`MsgSecretEntry` stores JID/ID keys as `Arc<str>`, a protocol-sized `[u8; 32]`, `expires_at` and `message_ts`. Upserts must merge expiry with `merge_msg_secret_expiry` (zero means never, otherwise later wins) and time with `merge_msg_secret_message_ts` (later non-zero wins). Retention deadlines and parent timestamps remain separate properties. Delete only non-zero expiry values at or before the cutoff.

A custom backend must implement the named read explicitly; it does not inherit a default that discards timestamp metadata. See [current contracts](/guides/current-api#hooks-and-backend-reads) and the source trait for exact method signatures and backend obligations.

## SqliteStore implementation

The native crate uses Diesel and SQLite. Default SDK features bundle SQLite; opt into `sqlite-storage` without the bundled feature to use your compatible system library. WASM uses the supported browser storage path and local futures rather than native blocking/thread-pool adapters.

`SqliteStore::open(url)` selects device 1. For multi-account or database tuning, open `SqliteDatabase` with `SqliteDatabaseConfig`, then select or provision an account.

```rust
use whatsapp_rust::store::{SqliteDatabase, SqliteDatabaseConfig, SqliteStore};

async fn accounts() -> whatsapp_rust::anyhow::Result<()> {
    let default_account = SqliteStore::open("whatsapp.db").await?;
    println!("{}", default_account.device_id());
    let db = SqliteDatabase::open(
        "accounts.db", SqliteDatabaseConfig::default().with_read_pool_size(1),
    ).await?;
    let new_account = db.create_device().await?;
    let selected = db.store(new_account.device_id());
    for summary in db.list_devices().await? {
        println!("account {}", summary.id);
    }
    drop(selected);
    Ok(())
}
```

## Account lifecycle

| Task | Database operation |
| --- | --- |
| Select an ID without opening connections or creating a row | `store(id)` |
| Check an existing row | `device_exists(id)` |
| Allocate and provision a new account | `create_device()` |
| Provision a chosen unused ID | `provision_device(id)` |
| Enumerate all accounts | `list_devices()` |
| Purge and recreate one existing account | `reset_device(id)` |
| Purge and remove one account | `remove_device(id)` |

Selection is not provisioning. `provision_device` is not an idempotent ensure and fails when the row already exists. SQLite allocates new IDs atomically and does not reissue removed IDs.

Stop the account's background work before reset or removal. Existing handles are not revoked; later writes through them can affect recreated state. Removing one account does not stop another account's client.

Old `SqliteStoreConfig`, per-device opening, sibling creation and database-management methods moved to `SqliteDatabaseConfig` and `SqliteDatabase`. See [current contracts](/guides/current-api#sqlite-database-and-account-scope).

## Database configuration

Configure database resources once. Defaults include one writer, one eligible reader, a 512 KiB page cache per connection and `Normal` synchronization. Reader concurrency applies only when the connection's WAL/cache/native conditions support it; it does not create an additional SQLite writer.

Keep writer `pool_size` at 1: concurrent deferred read-to-write transaction upgrades can deadlock, and `busy_timeout` cannot break that deadlock. Use `read_pool_size` for read concurrency.

Use supported builders such as `with_read_pool_size`, `with_mmap_size`, `with_connection_init`, `with_commit_barrier` and `with_incremental_vacuum`. The source documents each hook's order, target support and failure behavior. A commit barrier is a durability decision, not just a throughput knob.

## SharedSqlite

`database.shared()` provides database-wide read/run access using the same pools, permits and barrier. It is not device-scoped; custom tables must enforce their own account predicates. A shared adapter can outlive an individual database facade or selected account handle.

Use read access for read-only operations. A read permit is not permission to mutate data or to bypass the writer's transaction and durability policy.

### StoredDeviceSummary

`list_devices()` returns summaries with these fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | `i32` | Stored account ID |
| `pn` | `Option<Jid>` | Paired phone-number identity, when present |
| `lid` | `Option<Jid>` | Linked identity, when present |
| `push_name` | `String` | Stored display name |
| `linked` | `bool` | Registration state, following `Device::is_registered()` |

A provisioned row can exist before pairing, so existence alone does not imply `linked`. These summaries contain account identities; redact them in diagnostic logs.


## Resource reports

`SqliteDatabase::resource_report()` measures the database/pool scope; count it once per opened database, not once per account clone. `SqliteStore::scoped_resource_report()` describes the account scope. The legacy `DeviceStore::resource_report` reports the shared pool for compatibility, so adding it once per account double-counts that resource.

Reports are best-effort. Missing measurements remain absent rather than being invented as zero.

## Migrations and errors

The adapter applies its checked-in schema migrations at opening. Back up persistent accounts before changing storage formats. Follow the supported legacy session interoperability path when importing older records; do not hand-modify Signal state to bypass errors.

Inspect typed `StoreError` causes. Malformed message secrets use `InvalidMessageSecret`, and missing account operations can return `DeviceNotFound`. Preserve errors and timestamps instead of substituting empty values. See [error handling](/api/errors).

## TCToken storage

`ProtocolStore::store_received_tc_token` and `get_tc_tokens` support privacy-token persistence and batched reads. Received-token writes must preserve newer-wins semantics atomically; a byte-less placeholder can accept the first real token. The built-in SQLite adapter performs its check and write in an immediate transaction, while the in-memory backend holds its state lock. A custom adapter using a default read/modify/write must account for concurrent notification and identity-migration writes. See [privacy token behavior](/api/tctoken) and the [trait contract](https://github.com/oxidezap/whatsapp-rust/blob/93e5c7f75cdad98472efd218d9bff8a464cf47a7/wacore/src/store/traits.rs).
