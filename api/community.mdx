## create

Validate the name with `CreateCommunityOptions::new(name)?`. Use a typed `GroupDescription` for the optional description. The options and output DTOs are non-exhaustive; use constructors, then supported field mutation or builders.

```rust
use whatsapp_rust::{Client, CreateCommunityOptions, GroupDescription};

async fn create(client: &Client) -> whatsapp_rust::anyhow::Result<()> {
    let options = CreateCommunityOptions::new("Engineering")?
        .with_description(GroupDescription::new("Team discussions")?);
    let result = client.community().create(options).await?;
    println!("{}", result.metadata.id);
    Ok(())
}
```

## Recover partial creation

Creation and description configuration are separate remote operations. `CommunityError::ConfigurationFailed { created_jid, step, source }` means the community already exists. Resume configuration on that JID; blindly repeating `create` can create a duplicate. The error preserves the failed step and its `GroupError` cause.

For description recovery use `groups().set_description(created_jid, Some(description), PreviousDescription::Resolve)` to read the current optimistic concurrency token. This is a returned-error contract, not a cancellation or rollback guarantee.

```rust
use whatsapp_rust::{Client, CommunityError, CreateCommunityOptions,
    GroupDescription, PreviousDescription};

async fn create_or_resume(client: &Client) -> whatsapp_rust::anyhow::Result<()> {
    let description = GroupDescription::new("Team discussions")?;
    let result = client.community().create(
        CreateCommunityOptions::new("Engineering")?
            .with_description(description.clone()),
    ).await;
    match result {
        Ok(created) => println!("{}", created.metadata.id),
        Err(CommunityError::ConfigurationFailed { created_jid, step, source }) => {
            eprintln!("{created_jid}: {step:?}: {source}");
            client.groups().set_description(
                &created_jid, Some(description), PreviousDescription::Resolve,
            ).await?;
        }
        Err(error) => return Err(error.into()),
    }
    Ok(())
}
```

## create_subgroup_with_options

`create_subgroup(name, participants, parent)` uses default subgroup options. For explicit visibility use `CreateSubgroupOptions::new(name, participants, parent).with_visibility(SubgroupVisibility)`. The result is `CreateCommunityResult { metadata, .. }`; there is no separate `gid` output field.

## link_subgroups

`link_subgroups(parent, &[Jid])` uses default visibility. `link_subgroups_with_options` accepts `LinkSubgroupOptions::new(jid, visibility)`. A batch can contain both successes and failures; inspect `linked_jids` and every `SubgroupFailure`'s `jid` and `code`. Failures are named records, not `(Jid, u32)` tuples.

## unlink_subgroups

Inspect `unlinked_jids` and `failed_groups` for the same partial-result behavior. Do not retry successful entries merely because another entry failed.

## Query and manage

| Task | Entry point |
| --- | --- |
| List community overviews | `list_participating` |
| Fetch participating full metadata | `fetch_participating_metadata` |
| Enumerate or paginate linked subgroups | `get_subgroups` |
| Query counts | `get_subgroup_participant_counts` |
| Inspect or join one linked group | `query_linked_group`, `join_subgroup` |
| Fetch linked participant sets | `get_linked_groups_participants` |
| Remove community participants | `remove_participants` |
| Deactivate the parent | `deactivate` |

`get_subgroups` returns paginated `CommunitySubgroup` records with typed `GroupParticipant`s. Check `has_more` before deciding your list is complete. Membership approval is a distinct error for a subgroup join; it does not prove the caller joined.

For a community parent picture use the [pictures facade](/api/pictures) with an explicit `Community` target. Reactions, comments and encrypted edits address announcement posts through their message references; see [message actions](/api/send) and [the community guide](/guides/communities).
