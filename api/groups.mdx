title: Groups
description: Group management operations - create, modify, and manage WhatsApp groups

The `Groups` struct provides methods for managing WhatsApp groups, including creating groups, managing participants, and modifying group settings.

## Access

Access group operations through the client:

```rust
let groups = client.groups();
```

## Methods

<Tip>
The public group surface is split into purpose-built views. Pick based on what you're doing with the result:

| API | Returns | Use for |
|---|---|---|
| [`list_participating`](#list_participating) | `Vec<GroupOverview>` — id, subject, [hierarchy](#grouphierarchy), participant count | Populating a chat list, browsing the account's groups |
| [`fetch_overviews`](#fetch_overviews) | `Vec<GroupOverviewResult>` for a chosen subset | Refreshing a known set of chats without pulling every participant |
| [`fetch_metadata`](#fetch_metadata) | `GroupMetadata` — full state, participants, settings | Displaying or auditing a single group |
| [`routing_info`](#routing_info) | `Arc<GroupRoutingInfo>` — participants, addressing mode, LID/PN map | Reading the cached participant roster used by the send path |

Sending a message consults the routing cache for you. Call [`routing_info`](#routing_info) directly only when you need to inspect the participant list the send path will use — for example, to render a roster without paying for the full `fetch_metadata` payload.
</Tip>

### list_participating

List every group the account participates in as slim [`GroupOverview`](#groupoverview) records. One IQ round trip; participants and descriptions are never materialized, and no LID/PN backfill runs.

```rust
pub async fn list_participating(&self) -> Result<Vec<GroupOverview>, GroupError>
```

**Returns:**
- `Vec<GroupOverview>` — one overview per group. Each carries id, optional subject (the protocol can omit it), [`GroupHierarchy`](#grouphierarchy), and `participant_count`. No participant list, no settings.

Use this for chat-list style rendering. When you need the full state of one group, follow up with [`fetch_metadata`](#fetch_metadata).

**Example:**
```rust
use whatsapp_rust::features::groups::{GroupHierarchy, SubgroupKind};

let overviews = client.groups().list_participating().await?;

for overview in overviews {
    let subject = overview.subject.as_deref().unwrap_or("(no subject)");
    let count = overview.participant_count.unwrap_or(0);
    println!("{} — {} ({} members)", overview.id, subject, count);

    match overview.hierarchy {
        GroupHierarchy::Standalone => {}
        GroupHierarchy::Community => println!("  parent community"),
        GroupHierarchy::Subgroup { parent, kind } => {
            let label = match kind {
                SubgroupKind::Regular => "subgroup",
                SubgroupKind::Announcement => "announcement subgroup",
                SubgroupKind::General => "general chat",
            };
            println!("  {label} of {parent}");
        }
    }
}
```

### fetch_metadata

Fetch the complete, user-facing metadata of a single group.

```rust
pub async fn fetch_metadata(&self, jid: &Jid) -> Result<GroupMetadata, GroupError>
```

**Parameters:**
- `jid` — Group JID (must end with `@g.us`)

**Returns:**
- `GroupMetadata` — Owned, full metadata: subject, description, creator, per-participant admin roles, and ephemeral/membership settings (see the [type reference](#groupmetadata) for every field).

The query hits the network (no phash is sent, so the server never answers `not-modified`) and the result does not populate the send-path routing cache.

`fetch_metadata` returns protocol data only. It does not backfill missing participant phone numbers for LID-addressed groups. When you need PN-keyed display data, call [`resolve_participant_addresses`](#resolve_participant_addresses) on the returned metadata; the extra cache/database cost then reads at the callsite instead of hiding inside the fetch.

<Note>
**Concurrent calls for one group share a round trip.** A call that arrives while another is already in flight for the same group is answered by that in-flight query instead of sending its own, so the metadata it returns can describe an instant slightly before the call was made, bounded by how long the in-flight query has been running. Sequential calls are unaffected: each one sends its own query. If an earlier `fetch_metadata` call is already in flight, wait for it to finish before calling `fetch_metadata` again. Then issue a new sequential call when you need a result ordered after that earlier call.
</Note>

**Example:**
```rust
let group_jid: Jid = "123456789@g.us".parse()?;
let mut metadata = client.groups().fetch_metadata(&group_jid).await?;

let subject = metadata.subject.as_deref().unwrap_or("(no subject)");
println!("Subject: {}", subject);
println!("Mode: {:?}", metadata.addressing_mode);

// Opt in to PN backfill when you'll render phone numbers.
client.groups().resolve_participant_addresses(&mut metadata).await;
```

### resolve_participant_addresses

Backfill missing `phone_number` fields on the participants of a [`GroupMetadata`](#groupmetadata) from the client's LID-to-PN cache. The server often omits the PN attribute on `<participant>` nodes of LID-addressed groups, so consumers that key off PN would otherwise treat current members as absent.

```rust
pub async fn resolve_participant_addresses(&self, meta: &mut GroupMetadata)
```

**Parameters:**
- `meta` — Metadata (typically from [`fetch_metadata`](#fetch_metadata) or [`fetch_metadata_batch`](#fetch_metadata_batch)) to enrich in place.

No-op outside LID-addressed groups or when the PN is already present. Participants whose mapping is unknown are left untouched (`phone_number` stays `None`).

Kept separate from `fetch_metadata` so the extra cache/database cost is visible at the callsite. Prefer this over `fetch_metadata` alone when rendering participant phone numbers; skip it when only protocol data (subject, roles, settings) is needed.

**Example:**
```rust
let mut metadata = client.groups().fetch_metadata(&group_jid).await?;
client.groups().resolve_participant_addresses(&mut metadata).await;

for participant in &metadata.participants {
    let display_pn = participant
        .phone_number
        .as_ref()
        .map(|jid| jid.to_string())
        .unwrap_or_else(|| "(unknown)".to_string());
    println!("{} -> {display_pn}", participant.jid);
}
```

### routing_info

Return the cached, send-oriented routing view of a group.

```rust
pub async fn routing_info(&self, jid: &Jid) -> Result<Arc<GroupRoutingInfo>, GroupError>
```

**Parameters:**
- `jid` — Group JID (must end with `@g.us`).

**Returns:**
- `Arc<GroupRoutingInfo>` — the slim view the encryption path uses: participant JIDs, [`AddressingMode`](#addressingmode), the LID/PN mapping, and whether the group is a community announcement group. See [`GroupRoutingInfo`](#grouproutinginfo) for the full shape.

`routing_info` is cache-preferred. A warm entry returns immediately with no I/O. A cache miss sends one IQ request with the persisted participant phash, so an unchanged group costs a `not-modified` response instead of a full metadata download. The returned `Arc` is the same allocation the send path uses, so repeated calls on a warm group are effectively free.

Prefer this over [`fetch_metadata`](#fetch_metadata) when you only need the participant roster the send path will use — for example, when rebuilding a client-side participant list after a reconnect. Use [`fetch_metadata`](#fetch_metadata) for user-facing fields (subject, description, admin roles, group settings), which `GroupRoutingInfo` does not carry.

To force a fresh network read, call [`fetch_metadata`](#fetch_metadata) instead. The send path controls its own refresh policy through [`Freshness`](#freshness); the public `routing_info` is always cache-preferred.

**Example:**
```rust
use std::sync::Arc;
use whatsapp_rust::Jid;
use wacore::client::context::GroupRoutingInfo;

let group_jid: Jid = "123456789@g.us".parse()?;
let routing: Arc<GroupRoutingInfo> = client.groups().routing_info(&group_jid).await?;

println!("Addressing: {:?}", routing.addressing_mode);
println!("{} participants", routing.participants.len());

// Resolve a LID to the mapped phone-number JID (LID-addressed groups only).
if let Some(pn) = routing.phone_jid_for_lid_user("1234567890") {
    println!("LID maps to {pn}");
}
```

### create_group

Create a new group.

```rust
pub async fn create_group(
    &self,
    options: GroupCreateOptions,
) -> Result<CreateGroupResult, GroupError>
```

**Parameters:**
- `options: GroupCreateOptions` - Group creation options
  - `subject: String` - Group name (max 100 characters)
  - `participants: Vec<GroupParticipantOptions>` - Initial participants
  - `member_link_mode: Option<MemberLinkMode>` - Who can use invite links (default: `AdminLink`)
  - `member_add_mode: Option<MemberAddMode>` - Who can add members (default: `AllMemberAdd`)
  - `membership_approval_mode: Option<MembershipApprovalMode>` - Require admin approval (default: `Off`)
  - `ephemeral_expiration: Option<u32>` - Disappearing messages timer in seconds (default: `0`)
  - `is_parent: bool` - Create as a community parent group (default: `false`)
  - `closed: bool` - Whether the community requires approval to join. Only used when `is_parent` is `true` (default: `false`)
  - `allow_non_admin_sub_group_creation: bool` - Allow non-admin members to create subgroups. Only used when `is_parent` is `true` (default: `false`)
  - `create_general_chat: bool` - Create a general chat subgroup alongside the community. Only used when `is_parent` is `true` (default: `false`)
  - `linked_parent: Option<Jid>` - Atomically link this group as a subgroup of an existing community on create. Mutually exclusive with `is_parent` — when set, the new group is always classified as a subgroup even if `is_parent: true` is also passed. (added in v0.6)
  - `description: Option<String>` - Inline group description, emitted as a `<description>` child of the `<create>` stanza so it lands in one round-trip. Matches the existing community-create behavior. (added in v0.6)

**Returns:**
- `CreateGroupResult` with a `metadata: GroupMetadata` field carrying the full server response (JID, subject, addressing mode, participants with display names, parent/community linkage, etc.).

When the `PRIVACY_TOKEN_ON_GROUP_CREATE` AB prop is enabled, the library automatically resolves and attaches privacy tokens (`tc_token`) to each participant during group creation. This is handled internally — you don't need to manage tokens yourself.

**Example:**
```rust
use whatsapp_rust::features::groups::{GroupCreateOptions, GroupParticipantOptions};

let participant1: Jid = "15551234567@s.whatsapp.net".parse()?;
let participant2: Jid = "15559876543@s.whatsapp.net".parse()?;

let options = GroupCreateOptions::builder()
    .subject("My New Group")
    .participants(vec![
        GroupParticipantOptions::new(participant1),
        GroupParticipantOptions::new(participant2),
    ])
    .build();

let result = client.groups().create_group(options).await?;
println!("Created group: {} ({})", result.metadata.subject, result.metadata.id);
for participant in &result.metadata.participants {
    println!("- {} ({:?})", participant.jid, participant.participant_type);
}
```

<Note>
Since v0.6, `create_group` returns the full `GroupMetadata` (matching [`fetch_metadata`](#fetch_metadata)) instead of just the JID. Inspect `result.metadata` for participants, addressing mode, ephemeral timer, and parent linkage in a single round-trip. `GroupMetadata.participants` is a `Vec<GroupParticipant>` (the IQ-response shape), not the `GroupParticipantInfo` used by group notification events — but masked-number `display_name` labels are available here too, via `participant.details.as_ref().and_then(|d| d.display_name.as_deref())`, in addition to the event-side `GroupParticipantInfo.display_name` for live group-update events.
</Note>

### set_description

Set or delete the group description.

```rust
pub async fn set_description(
    &self,
    jid: impl Into<Jid>,
    description: Option<GroupDescription>,
    prev: PreviousDescription<'_>,
) -> Result<(), GroupError>
```

**Parameters:**
- `jid` - Group JID
- `description` - New description (max 2048 characters) or `None` to delete
- `prev` - The description this update replaces, as a [`PreviousDescription`](#previousdescription). The server accepts the update only when this token matches the group's current description id — a group that already has a description cannot be updated without it.

<Note>
[`PreviousDescription::Resolve`](#previousdescription) (the default) reads the current id from the server first, which always works but costs one extra query. If you already hold fresh [`GroupMetadata::description_id`](#groupmetadata), pass it directly — `metadata.description_id.as_deref().into()` — to skip that query. Use `PreviousDescription::Absent` for a group you know has no description yet, such as one you just created.
</Note>

Returns [`GroupError::DescriptionConflict`](#grouperror) if the group's description changed on the server between the read and this update (for example, another device changed it first).

**Example:**
```rust
use whatsapp_rust::features::groups::PreviousDescription;

let group_jid: Jid = "123456789@g.us".parse()?;
let desc = GroupDescription::new("This is our group chat")?;

// Resolves the current description id from the server automatically
client.groups().set_description(&group_jid, Some(desc), PreviousDescription::Resolve).await?;

// Skip the extra round trip with a token already on hand
let updated = GroupDescription::new("Updated topic")?;
let metadata = client.groups().fetch_metadata(&group_jid).await?;
client.groups()
    .set_description(&group_jid, Some(updated), metadata.description_id.as_deref().into())
    .await?;

// A freshly created group has no description yet
client.groups().set_description(&group_jid, Some(desc), PreviousDescription::Absent).await?;

// Delete description
client.groups().set_description(&group_jid, None, PreviousDescription::Resolve).await?;
```

### add_participants_with_history

Add participants to a group and share recent group messages with the new members who opted in. This covers direct additions only. It does not apply to invite links, QR joins, or sharing after someone joins.

```rust
pub async fn add_participants_with_history(
    &self,
    jid: impl Into<Jid>,
    participants: &[Jid],
    opted_in_receivers: &[Jid],
    history_messages: &[wa::WebMessageInfo],
) -> Result<GroupHistoryAddResult, GroupError>
```

**Parameters:**
- `jid` - Group JID
- `participants` - Members to add
- `opted_in_receivers` - The subset of `participants` who consented to receive history. An empty list performs only the add.
- `history_messages` - Messages from your own storage. The library doesn't read or persist history itself.

**Returns:**
- `GroupHistoryAddResult` with two independent fields:
  - `participants` - Per-participant results, the same as [`add_participants`](#add_participants)
  - `history_share` - A `GroupHistoryShareOutcome` describing what happened to the history share

**Message eligibility:**

The library filters `history_messages` before sharing. A message is included only if it:
- Has a nonempty ID and belongs to this group
- Is an acknowledged plain-text message
- Has a timestamp within the effective time window from account and group AB props
- Has no ephemeral (disappearing message) metadata

Media, pinned messages, and older history bundles are omitted. The newest eligible messages are kept up to the AB-prop message-count limit. Account-local metadata such as stars, labels, and receipts is stripped.

**Sharing rules:**
- You must be a group admin or superadmin, or the group must use `MemberShareHistoryMode::AllMemberShare`. See [`set_member_share_history_mode`](#set_member_share_history_mode).
- Community parent groups and CAPI-backed groups are not supported.
- The history bundle is encrypted pairwise to the opted-in, successfully added members and your own devices only.
- A group-wide notice is sent only after the server acknowledges the bundle and every addressed device was encrypted.
- If sharing is skipped or fails, the member add still stands.

**Example:**
```rust
use whatsapp_rust::GroupHistoryShareOutcome;

let group_jid: Jid = "123456789@g.us".parse()?;
let alice: Jid = "15551234567@s.whatsapp.net".parse()?;
let bob: Jid = "15559876543@s.whatsapp.net".parse()?;

// Load recent messages for this group from your own storage
let recent: Vec<waproto::whatsapp::WebMessageInfo> = load_recent_group_messages(&group_jid);

let result = client
    .groups()
    .add_participants_with_history(
        group_jid.clone(),
        &[alice.clone(), bob],
        &[alice], // only Alice opted in to receive history
        &recent,
    )
    .await?;

for p in &result.participants {
    println!("{}: {:?}", p.jid, p.status);
}

match result.history_share {
    GroupHistoryShareOutcome::Shared { message_count, .. } => {
        println!("Shared {message_count} messages");
    }
    GroupHistoryShareOutcome::Skipped(reason) => {
        println!("History not shared: {reason:?}");
    }
    GroupHistoryShareOutcome::UploadFailed { retry, .. }
    | GroupHistoryShareOutcome::BundleIndeterminate { retry, .. }
    | GroupHistoryShareOutcome::NoticeIndeterminate { retry, .. } => {
        // Retry without adding members again
        let outcome = client.groups().retry_group_history(&retry).await;
        println!("Retry outcome: {outcome:?}");
    }
    other => println!("History share outcome: {other:?}"),
}
```

<Note>
`Shared` confirms server acceptance of the bundle and notice. It does not confirm delivery to or reading by each recipient.
</Note>

#### Cancellation-safe flow

If your task can be cancelled mid-operation, split the call into two steps. `prepare_group_history_share` adds members, selects messages, and uploads the bundle. It returns `HistorySharePreparation::Ready(PreparedGroupHistoryShare)` or `HistorySharePreparation::Settled(GroupHistoryAddResult)` for skips and failures. `deliver_prepared_history_share` takes the prepared share by reference, so you can call it again if a delivery future is dropped.

```rust
use whatsapp_rust::HistorySharePreparation;

match client
    .groups()
    .prepare_group_history_share(group_jid.clone(), &members, &opted_in, &recent)
    .await?
{
    HistorySharePreparation::Ready(prepared) => {
        // Keep `prepared` until delivery completes
        let outcome = client.groups().deliver_prepared_history_share(&prepared).await;
        println!("{outcome:?}");
    }
    HistorySharePreparation::Settled(result) => {
        println!("{:?}", result.history_share);
    }
    _ => {}
}
```

Delivery rechecks current policy, your permission, and recipient membership before publishing.

#### retry_group_history

```rust
pub async fn retry_group_history(
    &self,
    retry: &GroupHistoryRetryToken,
) -> GroupHistoryShareOutcome
```

Resume a failed or indeterminate share using the token from a `GroupHistoryShareOutcome`. The retry reuses the same message IDs and audience and never re-adds members. It rechecks current policy and limits first. `GroupHistoryRetryToken` is an opaque in-memory value, not a persistence format. Treat it as sensitive.

#### GroupHistoryShareOutcome

| Variant | Meaning | Retry token |
|---------|---------|-------------|
| `NotRequested` | `opted_in_receivers` was empty | No |
| `Skipped(GroupHistorySkipReason)` | Sharing was withheld by policy or eligibility | No |
| `PreparationFailed` | Selecting or packaging messages failed | No |
| `UploadFailed` | Bundle upload failed | Yes |
| `BundleNotSent` | A local error occurred before the bundle was sent | Yes |
| `BundleRejected` | The server rejected the bundle | No |
| `BundleRetryableRejection` | The server rejected the bundle with a retryable code | Yes |
| `BundleIndeterminate` | No matching server ACK was observed for the bundle | Yes |
| `BundlePartialFanout` | The server ACKed the bundle but some devices weren't encrypted | Yes |
| `NoticeNotSent` | The bundle was ACKed but the notice couldn't be sent | Yes |
| `NoticeRejected` | The server rejected the notice | No |
| `NoticeRetryableRejection` | The server rejected the notice with a retryable code | Yes |
| `NoticeIndeterminate` | No matching server ACK was observed for the notice | Yes |
| `Shared` | The server accepted both the bundle and the notice | No |

### get_profile_pictures

Batch fetch group profile pictures. Each entry carries the server's per-item status code (`200`, `304` unchanged, `204` not found, `500` server error, `405` not-linked), so a caller can tell the states apart instead of only checking whether `url` is present.

### `Freshness`

Selects whether an operation may return an existing cached snapshot or must consult its source before returning. Shared across the SDK wherever a cache-backed lookup accepts an explicit staleness policy — for example `MessageRetransmission::with_group_metadata_freshness` and `StatusSendOptions::device_freshness` (see [Status](/api/status#statussendoptions)).

```rust
#[non_exhaustive]
pub enum Freshness {
    /// Return a cached snapshot when available and consult the source on a miss (default).
    CachePreferred,
    /// Consult the source and publish the resulting snapshot without clearing the
    /// previous one first.
    Refresh,
}
```

`Freshness` is re-exported from the crate root, so you can import it directly: `use whatsapp_rust::Freshness;`. When you pass `Refresh`, you never see a caller-visible gap — the previous snapshot stays servable until the new one is published.

### PreviousDescription

The description a [`set_description`](#set_description) call expects to replace — the server's optimistic-concurrency token for the group's description.

```rust
pub enum PreviousDescription<'a> {
    Resolve,      // default
    Absent,
    Id(&'a str),
}

impl<'a> From<Option<&'a str>> for PreviousDescription<'a>
```

- `Resolve` (default) — read the group's current description id from the server before sending. The only variant that's correct without knowing anything about the group, and the only one that costs a round trip.
- `Absent` — the group carries no description yet (e.g. one you just created), so no token is sent.
- `Id(&str)` — a description id you already hold, typically [`GroupMetadata::description_id`](#groupmetadata) from a recent [`fetch_metadata`](#fetch_metadata) call.

`From<Option<&str>>` lets you turn a held `GroupMetadata::description_id` into a token directly: `None` maps to `Absent` (that metadata says the group has no description), `Some(id)` maps to `Id(id)`. Use `Resolve` instead when the metadata's age is unknown, since stale metadata that missed a description added since would otherwise surface as `GroupError::DescriptionConflict`.

## Error types

### `GroupError`

All group methods return `Result<T, GroupError>`:

```rust
#[derive(Debug, thiserror::Error)]
#[non_exhaustive]
pub enum GroupError {
    #[error("{0}")]
    Iq(#[from] IqError),
    #[error("{0}")]
    Mex(#[from] MexError),
    #[error("invalid group request: {0}")]
    InvalidRequest(String),
    #[error("the group description changed since it was read")]
    DescriptionConflict,
    #[error("{0}")]
    Internal(#[from] anyhow::Error),
}
```

**Variants:**
- `Iq` — IQ request failed (timeout, server rejection, etc.)
- `Mex` — MEX protocol error (for methods using the MEX transport)
- `InvalidRequest` — malformed request (expired invite, missing fields, etc.)
- `DescriptionConflict` — [`set_description`](#set_description)'s `prev` token no longer matches the group's current description (the server answered `409 conflict`); another device changed it first. Kept distinct from a permission refusal so a caller can re-read the description and retry instead of giving up.
- `Internal` — catch-all for other errors

```rust
use whatsapp_rust::GroupError;

match client.groups().leave(&group_jid).await {
    Ok(_) => println!("Left group"),
    Err(GroupError::Iq(e)) => eprintln!("Server rejected: {}", e),
    Err(GroupError::InvalidRequest(msg)) => eprintln!("Bad request: {}", msg),

}
```
