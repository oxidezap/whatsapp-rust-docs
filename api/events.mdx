## Create an event

Use the builder for the non-exhaustive `EventCreationParams`. Only the name is required; creation rejects a blank name before sending. Times are Unix seconds.

```rust
use whatsapp_rust::{Client, Jid, EventCreationParams, EventResponseType};

async fn schedule(client: &Client, chat: &Jid) -> whatsapp_rust::anyhow::Result<()> {
    let params = EventCreationParams::builder()
        .name("Launch".to_owned())
        .description("Release planning".to_owned())
        .start_time(1_800_000_000)
        .build();
    let created = client.events().create(chat, params).await?;
    client.events().respond(
        &created.event_ref()?, EventResponseType::Going, None,
    ).await?;
    println!("{}", created.send_result().message_id);
    Ok(())
}
```

## Store the result

`CreatedEvent` owns the send result, crypto creator and `MessageSecret`. Use `event_ref()` to borrow those for an RSVP. Use `into_parts()` when transferring ownership to storage. Do not destructure the result as the old tuple or infer the crypto creator from a PN/LID display alias.

`Debug` redacts the whole creation result. Explicitly reading its secret or nested protobuf exposes sensitive data.

## Respond to a received event

Combine `InboundMessage::message_ref()` with the original creator and validated secret using `EventRef::new`. `respond(&EventRef, response, extra_guests)` produces an encrypted RSVP. `respond_raw` is the explicit byte/ID interoperability entry point.

For manual RSVP decryption, the core helper `wacore::event::decrypt_event_response_with_secret` requires that same parent association. Do not reuse a vote's secret or a new send's ID.

## Edit an event

Use `EditRequest::new(target, replacement).with_secret(created.creator(), created.secret())`. The target addresses the original content; the returned send result describes the edit operation. Read the [send task reference](/api/send#edit_message) before overriding operation IDs.
